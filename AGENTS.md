# Rudazov Mod — инструкции агенту

Этот файл подхватывается Grok автоматически в каждой сессии в этом репозитории. Не переспрашивать, «какой это проект».

## Документация

- Каноническая спецификация мода: `ARCHITECTURE.md`. Перед работой по магии, предметам, сети или capabilities — прочитать актуальные разделы.
- После изменения подсистемы обновить `ARCHITECTURE.md` в том же изменении. Не оставлять спецификацию старше кода.
- `README.md` — шаблон MDK/Forge, к моду не относится. Не читать и не править, пока пользователь явно не попросит.
- Комментарии в коде и ответы пользователю — на русском, идентификаторы и пакеты — на английском.

## Стек (жёстко)

- Minecraft **1.12.2**, Forge (FML, EventBus, Capabilities, `SimpleNetworkWrapper`).
- Байткод **Java 8**, синтаксис через Jabel (`enableModernJavaSyntax`). Records — с `@Desugar` (`com.github.bsideup.jabel.Desugar`). `sealed` Jabel 1.0.1 не умеет. Pattern `instanceof` можно. Нельзя API Java 9+: `List.of`, `Map.of`, `Optional.isEmpty`.
- Mod ID: `rudazovmod`. Пакет: `com.poleesteel.rudazovmod`.
- Не подключать чужие магические API и не поднимать версию Minecraft.
- **`build.gradle` не трогать.** Файл генерируется/меняется автоматически. Зависимости, репозитории и прочие ручные правки Gradle — только в файлах, которые для этого предназначены (`dependencies.gradle`, `repositories.gradle` и т.п.), и только если пользователь явно попросил.

## Границы кода

- Клиент: `client.render`, `client.input`, `client.render.hud`. Аннотации `@SideOnly(Side.CLIENT)` / `@Mod.EventBusSubscriber(Side.CLIENT)`.
- Серверная логика: `entities`, `magic` (старый прототип), `spell` (новый движок), `capabilities`. Рендер и ввод сюда не тащить.
- Регистрация предметов/блоков/сущностей — `init.RegistryHandler`, не размазывать по классам предметов.
- Сеть — `network`. Клиент в пакете каста шлёт **только номер слота**, никогда id спелла и никогда «я попал в X». Сервер сам решает.
- Не плодить новые Event-хендлеры, если логика умещается в предмет, сущность или спелл. Исключения: тик маны, capabilities, ввод, HUD.

## Магия

Текущее состояние и целевой движок описаны в `ARCHITECTURE.md` §§4–7. Кратко:

- Движок в `spell.*`. Игрок **конструирует** `SpellDefinition` из осей, не получает Java-класс спелла. `magic` — `MagicEventsHandler` (мана).
- Ядро: `CastMode` × `TargetType` × `Form` × `SpellElement` × power. Cost считать из осей. Каст только через `SpellEngine`.
- GUI сборки не делать, пока нет NBT определения, гримуара в capability и команды craft.
- `HOLD`+ENTITY/ITEM/BLOCK живые, но это **три** TargetType: не склеивать их в один спелл. Не предлагать в конструкторе комбинации, которых форма не умеет.
- Одно заклинание = **один** `TargetType`. Не склеивать сущность, предмет и блок в один спелл.
- `CHANNEL` — режим движка (удержание), не синоним телекинеза.
- Не воскрешать удалённый прототип: `AbstractSpell`, `TelekinesisLogic`, `PacketUseMagic`, `CustomSpell`, `SpellTelekinesis`.
- Id заклинаний в NBT и командах — полные `rudazovmod:name`. Строка без `:` считается namespace мода, не `minecraft:`.
- Пока не закрыт план движка в `ARCHITECTURE.md` §7, не добавлять GUI крафта, новые параллельные системы каста и новые Entity «под каждую стихию».

## Стиль

- Сохранять существующие имена классов и пакетов, не переименовывать «для красоты».
- Новые спеллы не добавлять как Java-классы. Тестовые комбинации — через `SpellRegistry.register` / `registerDefaults()`.
- Network ID сущностей стабильны: 1 цепь, 2 снаряд. Новые сущности — следующий свободный id, не перенумеровывать старые.
- Правки узкие: не рефакторить соседние подсистемы в том же изменении, если пользователь этого не просил.
